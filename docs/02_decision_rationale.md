# 기술/제품 선택 근거

## 1. 왜 모든 반도체 장비가 아니라 Load Port / FOUP Clamp인가

반도체 현장은 장비 제조사, 알람 체계, PLC 주소, I/O 맵, 매뉴얼, 정비 이력이 회사마다 다르다. 범용 자동분석 AI는 졸업작품으로는 넓고, 실제 현업에서도 보안과 데이터 접근 문제 때문에 검증이 어렵다.

따라서 특정 장비군을 깊게 완성하는 방식이 가장 논리적이다.

선택 이유:

- Load Port/FOUP는 반도체 장비 현장성이 높음
- Clamp/door/presence 센서와 DI/DO 설명이 명확함
- EtherCAT 상태 이상과 연결하기 좋음
- 신입 엔지니어 교육 시나리오로 설명하기 쉬움
- 실제 장비 제어 없이도 읽기 전용 진단 흐름을 만들 수 있음

## 2. 왜 온프레미스/내부망 구조인가

반도체 장비 데이터는 매뉴얼, 공정 조건, 장비 구성, 고장 이력 등 민감 정보를 포함할 수 있다. 외부 클라우드로 원본 데이터를 보내는 구조는 보안팀에서 막힐 가능성이 크다.

따라서 기본 설계는 다음과 같다.

- 원본 데이터는 내부망에 저장
- AI 분석도 내부 서비스에서 수행
- 외부 API는 옵션이며 기본 OFF
- demo data는 전부 synthetic/fake로 명시

## 3. 왜 읽기 전용인가

AI가 실제 장비를 제어하면 안전사고, 책임소재, 인증 문제가 발생한다. 졸업작품과 초기 제품에서는 장비 제어가 아니라 엔지니어 판단 보조가 맞다.

읽기 전용 범위:

- 알람 분석
- DI/DO 상태 해석
- EtherCAT 상태 해석
- 매뉴얼 근거 검색
- 체크리스트 생성
- 보고서 작성
- 선임 승인

금지 범위:

- PLC write
- Servo reset command
- Interlock bypass
- Safety door override
- Vacuum/pressure direct control

## 4. 왜 deterministic rule engine을 먼저 쓰는가

LLM은 설명에는 강하지만, 산업 안전 판단의 단일 근거로 쓰기 어렵다. 평가 시에도 LLM 응답이 매번 달라지면 시연 안정성이 떨어진다.

따라서 root cause ranking은 deterministic rule engine으로 수행하고, LLM은 선택적으로 문장 정리와 보고서 표현에만 쓴다.

## 5. 왜 Evidence Graph인가

단순 답변은 신뢰를 만들기 어렵다. FabMind Agent는 모든 원인 후보, 점검 단계, 보고서 문장에 evidence_id를 연결한다.

이 구조는 다음 질문에 답할 수 있다.

- 왜 이 원인을 1순위로 제시했는가?
- 어떤 알람 코드와 연결되는가?
- 어떤 DI/DO 신호가 근거인가?
- 매뉴얼 어느 문단을 참조했는가?
- 위험 조치는 왜 차단되었는가?

## 6. 왜 GitHub 중심 운영인가

졸업작품과 취업 포트폴리오 모두에서 결과물은 코드와 문서가 동시에 검증되어야 한다. GitHub README, CI, PR 기록, 테스트 결과, screenshots가 있으면 회사가 프로젝트를 평가하기 쉽다.
