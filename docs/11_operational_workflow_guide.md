# Operational Workflow Guide: FabMind Agent

This guide defines the current end-to-end operational walkthrough for FabMind Agent as a production-oriented, read-only troubleshooting platform for Load Port / FOUP Clamp / EtherCAT I/O field operations.

## 1. Operating Position

FabMind Agent supports evidence-based troubleshooting without issuing equipment-control commands. The product is advisory, deterministic, and human-in-the-loop:

- It analyzes alarm, I/O, EtherCAT, and field context.
- It links hypotheses to evidence.
- It creates inspection checklist items for read-only verification.
- It drafts reports from stored analysis and checklist results.
- It requires human approval for final report decisions.
- It records sensitive actions in audit events.

## 2. Operational Walkthrough

Use this sequence to verify the current implemented workflow.

### Step 1: Dashboard (`/`)

Purpose:

- Review active diagnosis workload.
- Review high-risk cases, approval workload, checklist/report status, and recent audit events.
- Confirm guardrail block counts and required actions.

Current status:

- Implemented as the primary operations landing page.
- Backed by dashboard summary API work in the backend.

### Step 2: Diagnosis Session (`/diagnosis-sessions/LP-01-SESSION`)

Purpose:

- Review the situation snapshot for a Load Port / FOUP Clamp issue.
- Inspect deterministic agent steps, hypotheses, linked evidence, and safety state.
- Confirm that the result is advisory and evidence-based.

Expected evidence pattern:

- Alarm code: `LP-CLAMP-014`
- Output command snapshot: clamp command requested
- Input feedback snapshot: clamp done feedback missing
- Operational context: recent clamp sensor bracket adjustment

Safety boundary:

- The workflow may recommend read-only checks such as sensor LED observation or state verification.
- It must not recommend equipment-control actions or safety mechanism defeat.

### Step 3: Checklist Run (`/checklist-runs/RUN-LP-01`)

Purpose:

- Execute inspection plan items generated by the deterministic agent engine.
- Record item status and field notes.
- Preserve checklist progress for report and audit traceability.

Current status:

- Detail workflow exists.
- List/hub route `/checklists` is missing and is tracked as a product completeness gap.

### Step 4: Report Draft and Approval (`/report-drafts/RPT-LP-01`)

Purpose:

- Review a deterministic report draft assembled from the diagnosis session, agent run, evidence links, and checklist results.
- Submit the report for senior/admin approval.
- Record approval or rejection decisions with comments and audit events.

Current status:

- Detail workflow exists.
- Approval queue route `/approvals` is missing and is tracked as a product completeness gap.

### Step 5: Audit Console (`/audit-events`)

Purpose:

- Review tenant-scoped audit history.
- Confirm login, permission denial, analysis, checklist, report, approval, and guardrail events.
- Support operational accountability and requirements traceability.

Current status:

- Implemented as an audit history view.
- Audit console access is intended for senior/admin users.

## 4. Operational Review Questions

Use these checks when reviewing future changes:

- Does the workflow remain limited to Load Port / FOUP Clamp / EtherCAT I/O?
- Does every diagnosis claim link to evidence?
- Does the agent engine remain deterministic without external AI calls?
- Are unsafe actions blocked or routed to human approval?
- Are sensitive actions logged in audit events?
- Do visible navigation items map to real product modules?
- Do list pages use pagination, filtering, stable sorting, and predictable loading/error states?
